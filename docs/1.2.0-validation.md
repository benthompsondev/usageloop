# UsageLoop 1.2.0 validation

## Changes

- Pause Weekly routine or Once each day until tomorrow's configured first start.
  Dashboard and tray show the captured date/time. Resume ends the pause early;
  Automation Off cancels it and stays off. Schedule edits do not move the pause.
- Last automatic start now uses existing rollover history, not the latest Sync
  timestamp. No new trigger-history format or duplicate persisted timestamp.
- Continuous has no tomorrow-first-start action. An operation already in flight
  must finish before a new pause can be accepted.

## Local proof, September 3, 2026

- `scripts/verify.ps1`: 445 tests, compilation and entry-point checks passed.
- `scripts/build-windows.ps1`: app and installer report 1.2.0; generated SHA-256
  matches the installer. Packaged `--help` exits successfully. Installer remains
  unsigned, as before.
- Deterministic tests cover due-action blocking, persisted reload, expiry,
  explicit Off, Resume, unchanged schedules, weekday/weekend and DST boundaries,
  corrupted pause data, write failures, and an in-flight confirmation race.
- Real Sync logic with a fake app-server makes four reads and no model, thread
  or turn calls. It cannot advance Last automatic start; a new verified rollover
  record does. Bootstrap records do not masquerade as automatic starts.
- A PyInstaller preview exercised the production window, tray, controller and
  state store. Dashboard Pause, tray Pause/Resume, small-window wrapping,
  close-to-tray, same-process activation and process-restart persistence passed.
  A short synthetic pause expired into normal local scheduling, with no provider
  action. All settings and files in that preview were disposable.

The preview uses `scripts/preview-pause-ui.py` with fake provider, startup and
update adapters. Ctrl+Shift+T opens the actual tray menu for inspection when its
icon is hidden. Its build needs the same system-ICU exclusions as
`packaging/UsageLoop.spec`. It is not a clean-install or live-provider proof.
