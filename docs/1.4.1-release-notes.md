# UsageLoop 1.4.1

This update helps UsageLoop recover when Codex changes its Windows runtime or
temporarily stops answering quota checks.

- On Windows, UsageLoop checks the registered Codex Desktop installation and its
  matching repair runtime before older managed copies. Runtime checks run away
  from the window so the app stays responsive.
- If a start check fails before sending, UsageLoop can retry the read-only check
  within a bounded period. If that period ends, it can check again at a later
  scheduled opportunity. Pausing or turning off automation stops those checks.
- Technical details shows which check failed, when quota was last read, and what
  you can safely do next. A start that may have been sent stays guarded against
  another send for the same opportunity.
- Starts respect an explicit Codex usage denial or spend-control block in
  addition to the existing window and weekly checks.

Thanks to **BFDqt** for the Windows runtime discovery fix and for moving runtime
checks off the UI thread ([PR #9](https://github.com/benthompsondev/usageloop/pull/9)).

## Upgrading

In **1.4.0**, open **About → Check for updates** once 1.4.1 is published. In
**1.3.9 and earlier**, use **Settings → Updates**. You can also use the installer
or archive from [GitHub Releases](https://github.com/benthompsondev/usageloop/releases).
Verify the matching SHA-256 checksum before running it. The Windows installer is
unsigned.

An upgrade keeps your local settings, routine, language, and start history.
If the old app stopped after a transient failure, UsageLoop can check the
connection again before following your saved schedule. **Recheck Codex
compatibility** and **Sync usage** are read-only. A scheduled start uses one
guarded request from your existing allowance.
