## Why the clock formula was not changed

Use synthetic local observations at seconds 100, 110, 120 and 130, with sliding
reset values 18098, 18108, 18118 and 18128. Submit at local second 160. Four later
observations report a fixed reset of 18158. This fits two different histories:

1. The server is two seconds behind the PC, and our request starts its window
   at local second 160.
2. The clocks agree, but preflight readings lag by two seconds. An external
   request starts the window at second 158, before ours is submitted.

Reconstructing the suggested relative lower bound from the summary gives
`18128 + (160 - 130) = 18158`, so it accepts both. This is a controlled model of
the approach, not an exact replay of the unavailable full proposal.
Integer rounding, changing observation delays and clock adjustments introduce
further uncertainty. Strong fixed-reset evidence establishes a running window;
it does not identify which request caused it. A more permissive calculation
needs additional trustworthy timing evidence, not a better-looking replay rate.

The new regression preserves the conservative result and confirms that another
bootstrap remains blocked. Existing normal-start, same-second rounding, delayed
submission, wrong-bucket and duplicate-request tests continue to pass.

## Changes and safety

The presentation distinguishes a future ANCHORED reset with a recorded
verification time from an unconfirmed earlier attempt. Sliding, expired or
unverified clocks keep the guarded presentation. The dashboard and tray share
this decision. Recent starts keeps its original record.

A synthetic integration test performs the real read-only Sync path against a
fake client, confirms the running clock, and verifies that the failed-guarded
history is unchanged. No model or thread-start API is available in that client.
The quota-display regression still checks that automation waits, the manual
start button stays hidden and the guarded outcome remains intact.

There are no production changes to the chain verifier, trigger, provider,
controller, history, scheduling or quota-decision modules. No installed state,
schedule or history was changed. No live Codex request was initiated.
