Codex 窗口计时说明

Codex 的 5 小时窗口何时开始？

对于提供 5 小时窗口的账号，UsageLoop 观察到：首个请求启动新窗口后，下一次重置时间才固定下来。仅仅到达上一个窗口的重置时间，并不一定会开始下一轮倒计时。

内容核对日期：2026 年 10 月 29 日。依据是 UsageLoop 开发过程中记录的观察结果及 1.4.0 的应用行为。撰写本文未发送实际模型请求。这些观察结果不是 OpenAI 的保证；账号限制及其行为可能变化。

翻译说明：本文简体中文由 AI 辅助翻译，尚未经中文母语使用者审校。英文原文可供对照。

提前启动不会增加额度，也不会绕过限制。启动操作是一次正常的 Codex 请求，会消耗订阅额度。如果账号没有 5 小时窗口，这种调度方式就不适用。

不断后移的预估时间与正在运行的倒计时

在窗口尚未启动时，多次只读观察可能显示：重置时间始终在大约 5 小时后，并不断向后移动。UsageLoop 将其称为未锚定。仅凭一个未来的重置时间，不能确认倒计时已经开始。

窗口启动后，多次观察可能显示同一个未来重置时间。UsageLoop 将其称为已锚定，并可据此显示倒计时。读取延迟、过时的观测数据以及时钟差异，都可能影响确认结果。

提前启动会改变什么？

  1. 凌晨 1:00：上一个窗口结束。在此示例中，尚未有新请求。
  2. 凌晨 4:00：一个小型定时请求启动下一个正常窗口。
  3. 上午 7:00：你开始工作，此时窗口已运行约 3 小时。
  4. 上午 9:00 左右：这个窗口重置。如果首个请求是在上午 7:00 发出，重置时间则会在中午左右。

这只是示例，不是对重置时间的承诺。只要还有可用额度，两种情况下你都可以在上午 7:00 工作。提前启动只会影响下一次正常重置的预期时间；启动请求本身也会消耗一些额度。

先检查自己的账号

  1. 打开 Codex 的用量页面，确认账号是否提供 5 小时限制。在 CLI 中，/status 会显示会话状态，并在可用时显示限额信息。OpenAI 的用量文档提供当前用量面板的入口。
  2. 在 UsageLoop 1.4.0 中，使用同步用量刷新用量观测。同步是只读操作，不会发送模型请求。如果刷新失败，保留的是上次已知信息，并不代表它已更新。
  3. 分别查看当前倒计时和最近启动记录。正在运行的倒计时描述当前窗口；某次启动被标为已确认，则是 UsageLoop 对该次尝试所作的保守判断。

窗口正在运行，并不能证明它是由 UsageLoop 启动的。另一个 Codex 会话也可能启动窗口。如果较早的一次启动仍未确认，UsageLoop 会保留该结果，不会自动重试该次请求。不要仅仅为了得到“已确认”标签，就重复发送结果不确定的启动请求。可参阅确认限制及受控反例（英文）。

每周额度是另一项限制

5 小时窗口重置不会重置每周额度。OpenAI 文档说明部分使用场景共享额度，并可能另有每周限制。UsageLoop 显示上次已知的每周用量信息，并在每周额度接近耗尽时阻止自动启动。它无法更改这些限制。请查阅适用于你所用方案的当前官方用量说明。

定时启动不等于使用储备重置次数

UsageLoop 不会使用 Codex 的 banked resets（储备重置次数），也不会购买额度。它只会在符合条件时，发送一个小型请求来启动下一个正常窗口。它无法提前结束正在运行的窗口，也无法补充每周额度。关于 banked resets 这一独立账号功能，请参阅 OpenAI 的说明。

什么时候定时命令就足够了？

通过 cron 或 Windows 任务计划程序运行一个小型 Codex 命令，可能已经能满足需要。UsageLoop 额外提供发送前的窗口与每周额度检查、不确定结果后的禁止自动重试保护，以及可查看的结果记录。它支持 Windows 和 Linux，需要 Codex 已登录，并且电脑处于唤醒状态、应用正在运行。电脑关机或睡眠时，它无法发送请求。

可以查看 UsageLoop 下载与安装要求。如果现有命令已满足需要，就不必再安装应用。
